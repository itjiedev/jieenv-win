  ShellExecuteEx 一律拒绝并级联降级到 PowerShell / schtasks，最终把“拒绝访问”抛给

  ctypes.get_last_error()：restype 缺省为 c_int，而裸调 GetLastError 取到的可能是两次

v1.15.0
- 修复 is_process_alive() 在 Windows 上把僵尸进程误判为存活的问题：进程退出后
  若仍有其他进程持有其句柄（父进程未回收、调试器附着等），内核对象会继续存在，
  OpenProcess 照样返回有效句柄，但 taskkill 与进程枚举都已找不到它。实测下陈旧
  PID 文件会让 stopserver 报 taskkill 退出码 128 且永远清不掉，也会让单实例判重
  把幽灵服务当真服务。改为再查 GetExitCodeProcess，STILL_ACTIVE(259) 之外即视为
  已终止；OpenProcess 拒绝访问（错误 5）按存活处理，与 POSIX 分支的
  PermissionError 语义一致；kernel32 调用补齐 restype/argtypes，避免 64 位下
  句柄被按 c_int 截断
- stop_server() 兜住 taskkill 报“找不到进程”的情况：复查目标确已消失则按已停止
  处理并清理 PID 文件，仍存活却杀不掉（如权限不足）照旧上报失败；两条提前返回
  路径补上停止请求文件清理，残留的请求文件会让下一个启动的服务自杀
- Windows 下补出优雅退出通道：新增停止请求文件 tmp/server.stop，服务进程内跑一个
  监视线程（start_stop_watcher），轮询到属于自己的请求后关闭 waitress 释放端口 →
  flush 日志 → 退出，超时未退才降级为 taskkill /F /T。此前 Windows 只有强杀一条路，
  会跳过 atexit、日志 flush 与 SQLite WAL checkpoint，而 Linux 早有 SIGTERM → 超时 →
  SIGKILL 的对称流程；stopserver 新增 --timeout 指定优雅退出等待秒数（默认 10）
- PID 文件新增 graceful 字段标记目标是否跑着监视线程：runserver 登记的是父（监视）
  进程，停止请求通知不到真正处理请求的重载子进程，故 graceful=False 直接强制终止，
  startserver 派生 runserver 时显式传该值（缺省按自身 argv 推断会得出错误结果）
- 重启语义收敛为策略注册：新增 register_restart_handler()，desktop.py 改为注册
  “进程内就地重启”，不再替换 jiecore.views / app_manager 的模块属性。原做法因
  views.py 用 from ... import restart_server 已把名字绑进自己命名空间，必须两处都打
  补丁，任何新增导入点都会静默失效并回退到杀进程重启
- 桌面壳就地重启补上与冷启动等价的启动期自愈（缓存对账 + 全部启用应用迁移）：
  就地重启不重跑 AppConfig.ready()，此前会出现“手工换了带新模型的应用文件后点
  重启，壳模式下表不会建”而进程重生模式会建的行为差异；同时改为返回结果字典，
  并在仅自启模式下注册（附着模式注册了也不会被调用，只会让职责产生歧义）
- views.api_restart 去掉自带的 runserver 终止分支，统一委托 restart_server()，消除
  两处各写一份 os._exit 造成的“谁是真相”歧义；所有 os._exit 前补 logging.shutdown()
- 新增 get_running_service() / is_service_running() 作为“服务是否已在运行”的单一真值
  源（校验存活 + start_time 防 PID 复用），server.py / startserver / desktop.py 共用，
  取代原先三套互不感知的判定（PID 文件 / 命名互斥体+端口探测 / 端口硬撞重试）
- server.py 增加启动前判重：已有登记在案且存活的服务时拒绝启动并打印原因。判重
  必须在 django.setup() 之前——ready() 在 setup 期间就会 write_pid_file()，之后再查
  读到的是自己刚写的记录（实测第二个 server.py 照样启动并改写了 PID 文件）；也不能
  只靠“端口绑定失败重试 10 次”硬撞，Windows 下 waitress 带 SO_REUSEADDR，第二个

  restart_server 拉新进程时注入 JIEENV_RESTARTING 让新进程跳过判重，避免被自己的
  单实例保护拦住
- desktop.py 判重同样改为以 PID 登记为主、端口探测为辅，并等登记的服务就绪后再开窗，

  自启 waitress 与真实服务撞端口”
- startup_db_sync 增加独占锁 tmp/startup_sync.lock：多个服务进程同时启动时只让一个执行
  自愈，其余跳过，避免并发 migrate 在 SQLite 上撞 database is locked；持有者已死、锁内容
  损坏或 start_time 不符（PID 复用）时自动抢占，不会留下永久死锁；锁文件创建失败则
  退化为无锁执行，不阻塞启动；同进程可重复进入，故就地重启可以直接复用

  桌面壳关窗共用；服务器对象经 register_wsgi_server() 登记，未登记时回退到
